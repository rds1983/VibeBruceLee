# Architecture

## Solution layout

| Project | Purpose |
| ------- | ------- |
| `VibeBruceLee` | Game executable. MonoGame DesktopGL, `net8.0`, nullable enabled. |
| `VibeBruceLee.Tests` | xUnit tests. References the game project; tests must not create a graphics device. |
| `Tools/VibeBruceLee.AssetGen` | Build-time asset generator (PNG/WAV). Not shipped. |

`VibeBruceLee.slnx` contains the projects. The game's `Assets/` folder is the runtime asset root and is copied to the output directory with `PreserveNewest`.

## Toolchain

- The SDK is pinned through `global.json` to .NET 10 (`latestFeature` roll-forward). The `.slnx` solution format requires SDK 9 or newer, and the README asks for SDK 10.
- The game targets `net8.0` for MonoGame compatibility; SDK 10 builds and runs it.
- `Directory.Build.props` enables nullable reference types, implicit usings, .NET analyzers at the recommended level, and treats warnings as errors.
- Formatting and style defaults live in `.editorconfig`: C# uses tab indentation; XML, JSON and YAML use two spaces.
- CI runs restore, Release and Debug builds, generated-asset verification, and tests on Windows and Linux (`.github/workflows/ci.yml`).
- `Tools/VibeBruceLee.AssetGen` is a small console project that produces PNG sprites (StbImageNext) and PCM WAV audio.

## Host

`BruceLeeGame` is the MonoGame `Game` host:

- fixed timestep at 60 Hz (`TargetElapsedTime = 1/60`),
- default window of 1280x960, resizable,
- F11 toggles borderless fullscreen; Escape or gamepad Back exits,
- vertical sync enabled.

## Presentation and screens

- The game renders into a 256x192 `RenderTarget2D`.
- `Letterbox.Calculate` picks the largest integer scale that fits the window and centers the canvas, leaving black bars. Nearest-neighbor sampling keeps pixels crisp at every scale.
- Window resizes update the back buffer; the canvas size never changes.
- `ScreenStack` holds the title, chamber, pause and game-over screens. Only the top screen updates; all screens draw bottom-to-top, so the pause screen overlays the chamber.
- Screens receive shared fonts and textures through `ScreenContext`; the game owns and disposes them.
- SpriteBatch uses `SpriteSortMode.BackToFront` with `SpriteLayers` (background, world, overlay, UI) so draw order is explicit.
- `SpriteSheetLayout` validates frame grids and maps frame indices to source rectangles; `SpriteSheet.Draw` supports integer scaling, horizontal flipping via `SpriteEffects`, and layer depth.
- `AnimationClip` holds frame indices and a per-frame duration. `AnimationPlayer` advances deterministically on a fixed-step clock, loops or finishes, and exposes the current frame. The title and chamber placeholders animate the four-frame lantern.
- The title, chamber and game-over screens are real screens now; the title starts chamber-01, the chamber runs the T-040 loop, and game over returns to the title. `ControlsScreen` is opened from the title with C/B and returns with Confirm or Controls.
- `TitleScreen` draws a two-line logo, a short story, a blinking start prompt, Bruce and lantern decorations, and keyboard/gamepad hints. It starts a new run on Confirm. `ControlsScreen` lists every default keyboard and gamepad binding in one-column form.

## Input

- `InputAction` is the shared vocabulary: movement, jump, attack, pause, confirm, cancel, fullscreen, sound and a temporary debug action.
- Default keyboard and gamepad bindings live only in `InputBindings.CreateDefault`. Screens and game code never check raw keys or buttons.
- `InputSystem` polls `KeyboardState` and `GamePadState`, computes held/pressed/released edges and keeps 120 ms buffers for jump and attack. Gameplay consumes a buffer with `ConsumeBuffered`.
- Analog sticks use a 0.5 dead zone; D-pad and keyboard aliases work alongside them.
- Losing focus clears all state and buffers. A gamepad disconnect/reconnect also clears the frame state so nothing sticks, and the next frame suppresses accidental presses from buttons held during the transition.
- `DebugGameOver` (G) is a debug shortcut to the game-over screen; normal play reaches it by losing the last fall.

## Assets

The project does not use the MonoGame content pipeline. Raw runtime files are copied from `VibeBruceLee/Assets` to `Assets` next to the executable; readmes are excluded. The game creates an XNAssets `AssetManager` and uses `LoadTexture2D`, `LoadFontSystem`, `FontSystem` and `SpriteBatch.DrawString` directly. There are no wrapper services. Missing keys raise XNAssets' `AssetNotFoundException` with the resolved path.

Sprites and audio are generated by `Tools/VibeBruceLee.AssetGen`, which emits PNG and WAV files from code. The title screen exercises both the test card and lantern textures plus FontStashSharp text. Hot reload is not implemented; restart after changing assets. See `Design/assets.md` and ADR-0002.

## Physics

- `PhysicsBody` owns position, size, velocity, grounded and current-vine state. Callers set the desired horizontal velocity and jump/climb velocity each frame; `PhysicsWorld` applies gravity and resolves movement.
- `PhysicsWorld` is a fixed 256x192 world with configurable gravity and fall-speed cap.
- Movement is split into sub-pixel substeps on each axis, so fast bodies cannot tunnel through thin platforms or walls.
- Solid platforms block from every direction; one-way platforms only catch a falling body crossing their top.
- Screen edges clamp bodies; the bottom clamp counts as grounded.
- Vines have vertical or horizontal orientation. Attached bodies ignore gravity and move only along the vine axis; leaving the vine rectangle detaches them.
- Physics uses float positions but no randomness, so identical input sequences produce identical results.

## Debug tooling

`DebugState` holds overlay, slow-motion, pause, invincibility and skip-chamber flags. `DebugController` and `DebugOverlay` are instantiated only in `DEBUG` builds, so release builds have no debug keys or overlay. See `Design/debug.md` for keys and behavior.

## Player locomotion

- `Player` wraps a `PhysicsBody` and runs a small state machine: idle, run, jump, fall, duck, climb, attack, hit, knocked down, dead.
- Health uses three blows per fall. Hits grant brief invulnerability, and the third blow starts a 60-frame death animation.
- After a fall, `Respawn` restores blows, position and a 90-frame invulnerability window.
- Horizontal movement accelerates toward run speed and decelerates with friction; ducking stops horizontal motion.
- Jumping consumes the buffered jump when grounded and cuts upward velocity when the button is released for variable height.
- Pressing up on a vine attaches; climbing moves only along the vine axis, gravity is ignored, and jump detaches. Reaching a platform at the vine top snaps Bruce onto it and returns control.
- Sprites are anchored at the feet so characters stand on platforms rather than hovering.
- Contextual attacks use centralized frame data (`AttackDefinitions`): standing chop, running kick (the reviewers' "flying kick"). The kick is a longer, momentum-carrying move; the chop stops Bruce. Airborne attacks are not part of the original moveset. Active hitboxes are checked by other entities, each attack hits once, and taking a hit cancels the attack into hitstun or knockdown.
- Hits trigger four frames of hitstop and an eight-frame red flash. Landings spawn a short deterministic dust burst.
- `Player.SoundRequested` raises jump, land, chop, kick, hit, knockdown, death and respawn events for the audio system added in T-052.
- Falls are safe; landing is handled by the physics world.
- Animation frames are mapped per state from the Bruce sheet (idle 0-1, run 2-5, air 6, duck 7, attack 8-13, climb 14-15, hit 16, knockdown 17, death 18-19).

## Enemies

- `EnemyDefinitions` holds shared type data: hit points, body size, run, patrol and climb speeds, sight and attack ranges, cooldowns, timers, jump parameters, primary/secondary attacks and whether the body blocks movement. `EnemyDefinitions.Ninja` and `.Yamo` are the current values.
- On the target surface, an enemy chooses its attack by distance. The Yamo punches inside 24 px and uses the slower 25-38 px crush kick otherwise. The chosen attack supplies its own cooldown (45 frames for the punch, 100 for the kick), so the state machine does not need a special-case Yamo branch.
- `Enemy` wraps a `PhysicsBody` and runs one deterministic state machine for both types: idle, patrol, chase, attack, jumping, stunned, knocked down and respawning. A null target keeps it patrolling, so tests do not need the player type.
- `EnemyNavigator` builds a graph of platform tops. Same-level platforms connect by walking, vertical vines connect the surfaces they touch, and higher surfaces connect to lower ones by walking off the edge. Breadth-first search returns walk, climb and drop waypoints. Routes use no randomness.
- The enemy walks to the chosen vine, climbs it by moving directly along the vine axis, and steps onto the target platform. Dropping is handled by walking off the ledge and letting physics fall.
- Once on Bruce's surface, `KeepTargetDistance` stops the enemy two pixels inside its attack range and backs it away when Bruce gets closer. This prevents enemies from walking into and standing on the player while attacks are on cooldown.
- Yamo sets `BlocksMovement`. `ChamberScreen` calls `Player.ResolveBodyBlock` against each visible blocking enemy before enemy updates, pushing Bruce out to the nearer side and zeroing his horizontal velocity. This makes the wrestler a wall without adding a second dynamic body to `PhysicsWorld`.
- `EnemyEncounter` is the headless combat coordinator. Its update order is: update Bruce, resolve blocking bodies, pick the single attack token holder, update enemies (only that enemy may start an attack or leap), resolve player and enemy attacks, then separate overlapping enemies. `ChamberScreen` delegates to it and keeps only presentation, death and HUD logic.
- The attack token is held by any enemy already in `Attack` or `Jumping`. An enemy that starts an attack during its update takes the token for the rest of that frame, suppressing later enemies in the list. A 30-frame pressure counter blocks new attacks after an enemy hits Bruce.
- Enemy attacks check other enemies before Bruce. A friendly hit awards no score and can knock the victim down. `Enemy.CanBeHit` rejects respawning, knocked-down and invulnerable targets so a one-hit attack is not wasted and no score is awarded for an invalid hit.
- Separation is weighted by body width, runs two passes for stability, is clamped to the virtual width, and skips enemies that are climbing, stunned, knocked down or airborne.

## Hazards

- `HazardSystem` builds one `Hazard` from every chamber `hazards` entry. `Hazard` wraps the data rectangle and exposes `IsActive`, `IsWarning`, `IsVisible` and `IsFinished`.
- `TimedBeamHazard` covers electric and PAN lights with a repeating off-warning-active cycle. `BushHazard` and `MineHazard` are one-shot and despawn. `MovingWallHazard` treats the data rectangle as a horizontal travel range for an eight-pixel crusher. `ProjectileHazard` moves in `directionX` at `speed` and despawns off-screen or after eight seconds.
- `HazardSystem.Update` resolves damage centrally: active hazards call `Player.Kill` and `Enemy.ApplyHazard`; non-active hazards receive `OnOverlap` so mines can start their fuse. Finished hazards are removed, and `Reset` recreates the chamber's original set.
- Hazard contact kills with a whole-fall penalty for Bruce and an unscored knockout for enemies. `Enemy.ApplyHazard` bypasses hit-point damage and sends the enemy through knockdown/respawn.
- Hazard visuals are placeholder rectangles colored by kind and warning/active state until T-053 supplies final art.

## Fire Wizard

- `WizardBoss` is built from the chamber's `wizard` definition. It owns the wizard and button rectangles, a 1.4 s fireball cycle, a 0.3 s warning window, alternating eyes and a two-second defeat timer.
- Fireballs are dynamic `AimedFireballHazard` instances added to the chamber's `HazardSystem`. They aim at Bruce's centre when spawned, move at 90 px/s, damage through the normal hazard path and despawn off-screen or after eight seconds.
- `TryPressButton` requires the player to overlap the button and press Attack. It awards 3,000 points in `ChamberScreen`, clears active fireballs, and stops further spawning.
- Boss chambers may have no exits. `ChamberValidator` requires a `wizard` definition for `boss: true` and rejects a wizard on normal chambers.
- After the defeat timer, `EndingScreen` shows the cleared loop. Confirm calls `GameSession.AdvanceLoop`, resets hub progress and starts chamber-01 with the same score and falls. The loop scaling below applies immediately.
- The Ninja can also leap. `EnemyDefinitions` supplies jump speed, forward speed, windup, range, cooldown and an airborne attack. A leap starts only when the target is 23-80 px away, at most 24 px above, and either on the same surface or on a surface with no walk/vine route. The arc is fixed at launch, with a 12-frame ground windup, and the body is airborne for about 40 frames.
- The airborne strike uses `NinjaJumpAttack` with 8 startup, 14 active and 12 recovery frames. `TryGetAttackHitbox` selects the bokken or the leap strike from the current state, and either can hit once.
- `SeededRandom` is a small xorshift32 source for patrol direction and idle variation. It replaces `System.Random` so replays are stable across runtimes.
- Attacks reuse `AttackDefinition` frame data. Each enemy attack has startup, active and recovery frames, and can hit once. Player hits stun or knock down enemies; the final hit returns `true` from `ApplyHit` so the chamber can award the knockout bonus.
- `ChamberScreen` creates one enemy per `enemySpawns` entry, resolved onto the platform below the spawn point, and passes Bruce's feet as the target (or null while he is dead). It resolves player-to-enemy and enemy-to-player hitboxes after both updates, and draws enemy hurtboxes and attack boxes in the debug overlay.

## Run session

`GameSession` owns the score and fall reserve:

- five starting falls,
- an extra fall every 30,000 points,
- fall loss and game-over state,
- loop count: 1 on a new run, advanced after the wizard ending,
- reset when a new run starts from the title.

`EnemyScaling.Apply` produces a per-loop `EnemyDefinition` copy: speed +15% and cooldowns -10% per loop (capped), sight +10% (capped), and `RespawnFrames = 0` from loop 2. `Enemy.BeginRespawn` respawns immediately when the definition has no respawn delay. `ChamberScreen` applies this to every enemy spawn.

`HazardSystem` accepts a second `loopHazards` list and includes it from loop 2. Chamber-16 uses this to fill beam gaps and cover a platform. `EndingScreen` advances the loop and starts chamber-01 with score and falls preserved.

The chamber HUD reads score, blows, falls and lantern progress from the player, session and chamber progress. The sample chamber pushes the game-over screen when the last fall is consumed.

## Chamber runtime

- `ChamberCatalog` holds every loaded chamber in sorted file order. `First` is the start chamber, `Get(id)` resolves exit targets, and `TryGet` handles optional lookups.
- `ScreenContext` carries the catalog instead of a single chamber. `TitleScreen` starts `Chambers.First`.
- `ChamberProgress` owns per-attempt lantern state. It collects a lantern when Bruce's hurtbox intersects its 16x16 box, computes required and optional counts from its set, opens exits when required lanterns are complete (`requiresLanterns: false` bypasses the gate), additionally checks the hub hatch flag for `requiresHub` exits, finds an open exit under Bruce, and resets on death.
- Hub chambers (`hub: true`) pass the set owned by `HubProgress` (on `GameSession`) into `ChamberProgress`, so collected lanterns persist between the three rooms. The middle room's `requiresHub` floor hatch opens only when every required lantern across the hub is collected. Dying resets only the current room's set; a new run clears all hub progress.
- The chamber HUD shows pooled `HUB x/y` progress in hub rooms and `HATCH OPEN` when the hub gate clears. Non-hub rooms show `EXIT OPEN` when their own required lanterns are complete.
- `ChamberScreen` awards 125 per lantern and 2,000 for entering an exit. On an exit it replaces itself with the target chamber from the catalog. On a non-final death it respawns Bruce, resets lanterns, enemies, encounter pressure and dust, and keeps score and falls.

## High scores and pause

- `HighScores` owns the all-time table (maximum five entries) and persists it to `%LOCALAPPDATA%/VibeBruceLee/highscores.json` (falling back to the app directory if LocalApplicationData is unavailable).
- Load treats a missing file as empty and catches malformed JSON, I/O and access errors, so a bad save never crashes the game. Entries are sanitized to three letters and positive scores, sorted by score, loop and initials, then trimmed.
- Saves write a temporary file and move it over the live file; write failures leave the in-memory table usable.
- `ScreenContext.HighScores` is shared by the title, HUD, game over, initials and high-score screens. The chamber HUD shows `TOP nnnnnn` at the bottom; the title shows the same.
- `GameOverScreen` shows the table and, when the run qualifies, prompts for initials. `InitialsScreen` uses Up/Down to change a letter, Left/Right to select a position and Confirm to save. `HighScoreScreen` then shows the updated table and returns to the title.
- `PauseScreen` is an overlay with resume, controls and quit hints. Controls help opens as a normal screen on top of the pause overlay and pops back to it.
- Lanterns disappear once collected and return on a chamber reset. The HUD shows required progress and displays `EXIT OPEN` when the gate clears.
- Chamber-specific hazards remain inert until T-042, then T-043/T-044 use them in the mid- and late-game. Chambers 01-03 are the entrance hub, 04-19 form the two underworld chains, and chamber-20 is the Fire Wizard boss. T-046 adds looping.

## Chamber data

Chambers are JSON files under `VibeBruceLee/Assets/levels`, described in `Design/chambers.md`. `ChamberLoader.LoadAll` deserializes them with `System.Text.Json` (strict unknown-field rejection), `ChamberValidator` checks geometry, types, duplicate ids and exit targets, and failures throw `InvalidDataException` with field paths. The current two files are a first pass; chamber-01 is the T-040 entrance slice and later tasks author the full fortress.

## Testing

- `dotnet build VibeBruceLee.slnx`
- `dotnet test VibeBruceLee.slnx`
- `dotnet run --project VibeBruceLee` (add `--fullscreen` to start in fullscreen)

Unit tests cover letterbox math, screen-stack lifecycle, input actions and buffers, debug toggles, sprite-sheet layout, animation timing, chamber loading/validation, physics and collision, player locomotion, combat, health/falls/session logic, asset generation and type-level smoke checks. Anything requiring a window is verified manually and, later, through headless simulation (T-060).
